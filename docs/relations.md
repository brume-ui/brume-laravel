# Transactional form relations

Form saves now lock and refresh the scoped root on its own connection before model-aware editing declarations, validation and the saving hook. Rendering still initializes once; an edit save reruns the editing hook against the locked record, restoring pre-hook declarations first. The caller's model object is preserved. Creates keep a null root evaluation context. The saving hook receives validated values and may adjust values or ordinary model attributes. The actual adjusted graph is validated again before any model save or upload copy; root identity and connection cannot change in that hook.

All submitted active editable source selections must belong to the current base `OptionSource::query`, including unchanged selections. An unchanged selection that is no longer eligible rejects the entire save. Omitted fields remain untouched. Readonly/inactive selections retain authoritative state without a new eligibility requirement; removing a selection does not require the removed source to remain selectable. Source sections only filter browsing. Remote Select and MultipleSelect use the same eligibility rules; remote Tags remain free text suggestions. Dependencies come from the complete submitted graph with authoritative readonly and inactive stored values, canonical values and actual row identity, including cross-row numeric paths and whole collections. Source queries are local builders, never HTTP requests.

| Declaration | Persistence |
| --- | --- |
| `relationPicker(...)->relation('owner')->multiple(false)` with BelongsTo | Assign the selected owner's key; null requires a nullable owning foreign key. Declared extras update only the selected related model's declared editable fields. |
| Picker with direct HasMany | Reassign selected children to the parent; null the nullable foreign key of removed children. |
| Picker with BelongsToMany | Preserve selected pivot rows and undeclared columns; extras read/write pivot columns. Source primary IDs remain wire identities; insert/update and detach use separately frozen relationship keys, including non-primary related keys. |
| Picker with intermediary HasMany and `associateBy('product_id')` | Match the parent's intermediary by source ID; update its declared fields, preserving its primary key and counters. |
| Multiple owned intermediary/BTM picker with `orderColumn('position')` | Persist zero-based selection positions on intermediary/pivot storage; fresh snapshots order by that qualified column and a stable source/row identity tie-breaker. Retained identities/counters survive; without this mapping database relation ordering governs fresh reads. |
| Intermediary with `restoreRemoved()` | Include the parent's soft-deleted rows when matching; restore the same row on reselection. Multiple historical matches reject atomically. |
| `repeater(...)->relation('children')->orderColumn('position')` | Create/update/delete children recursively; retained rows keep their identities and undeclared attributes. Order is zero-based. |

Repeater rows carry `_brume: {key, id?}`; picker selections carry a source `id`. Numeric model identities must use canonical string spelling; string keys are exact, including case and leading zeroes. Duplicate keys and IDs reject. IDs are resolved through the authoritative parent relation, then source eligibility where applicable. Identity/FK/association/order attributes cannot be declared as editable row aliases; pivot keys and timestamps are also protected. Every read, lock and write belongs to the root model connection; mixed-connection graphs reject before persistence.

Evaluation callbacks for existing related rows use the actual parent-owned model, while newly associated/created rows have null evaluation context. For BelongsToMany extras, the existing evaluation model is the actual pivot, and a new association has null evaluation context. JSON evaluation uses the original nullable global root, including JSON inside relation rows or picker extras. Storage ownership is separate: a newly associated existing BelongsTo/direct HasMany source is locked before resolving its already-owned descendants, readonly stored attributes and old uploads. Those descendants use their actual owned evaluation models. Ordinary stored values come from the storage model; a declared value reader retains its evaluation context. JSON container reads also separate the persisted model used to preserve encoded JSON shapes from the reader context. A null reader context keeps the existing default-value behavior without invoking the custom reader.

`Field::fill(Model, mixed)` and `saveUsing(Model, mixed)` are mutating writers and always receive a real non-null execution target. A new BelongsToMany association receives its unsaved pivot, a newly associated BelongsTo/direct HasMany row receives the scoped existing selected model, and a JSON row writer receives its local conversion carrier. The writer target does not change existing/new evaluation semantics; passing null or the global root to a JSON writer would misdirect persistence. JSON custom objects/lists and exact decimal strings keep their existing semantics.

There is no depth limit for supported ownership chains. An explicit Eloquent relation cannot be owned by a JSON row: that row has no model/FK owner. For example, a JSON `repeater('data', ..., fn ($row) => $row->repeater('children', ...)->relation('children'))` is rejected at declaration resolution. Make the outer repeater relation-mode when rows own related records, or store selected IDs in JSON remote Select/MultipleSelect fields. Layout sections/embeds do not change the persistence owner. JSON inside relations and recursive JSON inside JSON remain supported.

## Internal planning and upload lifecycle

`RelationPlanner::plan(Form, Model, array, ?Model): RelationPlan` runs only inside the root transaction. It resolves and locks the complete graph, prepares authoritative condition/source projections, validates declared fields, then freezes scalar, association, order, restoration and removal operations. `RelationSynchronizer::save(RelationPlan): void` executes that tree. No row is filled/saved and no file is copied while planning.

The plan returns defensive copies through `values()`, `operations()` and `inventory()`. Its model/declaration snapshots cannot be mutated by changing those returned copies. The synchronizer updates the caller's root model after executing the frozen tree. `withOriginalInventory()` preserves all pre-saving-hook known-owner inventory and supplements the final locked raw traversal only for genuinely new persisted owners introduced by a saving hook. Owner identity includes connection/table/primary key, or the authoritative foreign/related key pair for a pivot without a primary key. A new declaration on an already-known owner cannot replace its pre-hook raw values. `withArchivedValues()` returns a new plan replacing only previously validated Upload leaves throughout relation operations and JSON aggregates after one whole-graph archiver converts tokens to final paths; it does not re-plan or authorize a graph after file copies.

`inventory()` contains:

- `original`: complete locked pre-hook field inventory, including omitted/removed descendants and existing storage first selected into a new BelongsTo/direct HasMany association. Entries have `field`, numeric `path`, canonical `template`, ordered `rowContext`, cloned storage `owner`, raw semantic `stored` value and `rawAttributes`.
- `fields`: current resolved field inventory keyed by numeric path, with the same declaration/context/owner information, canonical `storageContext`, separate nullable evaluation `callback`, storage `model`, `json`, `submitted` and `validated` flags. Validated entries additionally have `value` and `active`; consumers must require both `validated` and `active` for editable upload work. Preserved inactive JSON values are not new upload submissions.
- `rows`: resolved row contexts and authoritative storage owners, keyed by numeric row prefix.
- `removed`: removal records with the containing path/template/storage context, relation `kind`, scoped row identity, original model and child form declaration. The complete old file traversal is in `original`.

Upload requests keep their numeric `field` for error locations and send JSON `rowContext` with the exact ordered declared ancestor paths and stable row identities. Optional multipart `ancestorSources` reuses the options protocol: an array of `{path, rowContext, depends, dependencyContexts?}` instances. Canonical picker path plus owner prefix identifies each instance; no model/query names or client authorization proofs are accepted. Source eligibility is checked before resolving a newly selected owner's descendants. The shared read resolver separates actual scoped storage from nullable evaluation contexts, including readonly scalar/whole-collection dependencies and JSON's original global root context.

Temporary tokens bind user, guard, explicit form ID, root record, canonical Upload template, ordered verified row chain and expiry on the root connection. The locked token and binding tuple are compared exactly in PHP as well as filtered in SQL, so a case-insensitive database collation cannot alias distinct declarations such as `file` and `FILE`. Numeric row reorder therefore works; cross-row/root/user claims, duplicate token use, duplicate keys and forged existing paths reject before any file copy or model write. JSON object property order is immaterial; row order, typed keys and IDs remain exact. Existing paths and metadata come from locked raw storage, including readonly extras. Stored Upload envelopes and their extra dictionaries accept structural arrays or objects without flattening opaque values inside declared extras. Omitted JSON values, unknown raw members and object/list shapes survive row movement.

`UploadArchiver::archivePlan()` performs one complete upload preflight and freezes transformed leaves/cleanup before execution. The existing `archive()` and Form compatibility subclass remain available for root callers. No graph decision is rebuilt after copies. Temporary claims are deleted under lock inside the model transaction; outer rollback restores claimability and retains temporary content, removes new final copies and preserves old files. Only actual outer commit removes temporary and replaced/removed files. Cleanup failures are isolated per file and reported after persistence.

Hard owned-child/pivot removal cleans owned descendant files, stopping at BelongsTo/direct HasMany source association boundaries. Detach/reassignment retains source-owned files; soft deletion retains files. JSON-row removal cleans its owned files, while an omitted container retains them. Resource hard deletion inventories all declared owned descendants independently of editability; existing source associations retain their files.

Upgrade installed connections with the package's additive `2026_10_31_000001_add_row_context_to_brume_uploads_table.php` migration before using nested uploads. It widens `field` to LONGTEXT for lossless canonical paths at arbitrary configured depth and adds nullable JSON `row_context`. Existing rows are preserved: legacy null context remains usable only for a root Upload with an empty chain and never grants nested ownership. The original create-table migration is unchanged. Per S3-R30, migration rollback drops `row_context` while deliberately retaining the widened `field`; narrowing it could silently truncate live long bindings. No production migration is performed by these tests.

SQLite and MySQL tests exercise validation, persistence and actual outer commit/rollback on isolated connections. Specific concurrent locking behavior and normal CI/browser/release acceptance remain separate gates; ordinary transaction tests do not prove contention safety.

The renderer checks live upload ownership immediately before accepting a result and before emitting its draft value, including form/reset identity, endpoint, stable row lifetime and ancestor source values/contexts/private ownership. It follows the stable owner through movement, writing to its current path even before React renders; removed/re-added rows and changed dependencies cannot receive stale responses. Private lifetimes are never sent to the server.


`RelationPicker::orderColumn(string)` is an optional server storage mapping; `orderAttribute()` returns
it. It adds no schema or submitted metadata. Only multiple owned intermediary HasMany (`associateBy`)
and BelongsToMany pivot selections support it. Single/BelongsTo and direct source-owned HasMany
configurations reject: an association's selection order must not update a shared source model.
The host owns the configured column and its migration; the package creates no implicit ordering column.
The configured column cannot collide with identity/FK/association/pivot timestamp columns or declared
editable/mapped extras. Submitted undeclared `position` values do not control it. Positions are frozen
with the validated whole graph and written to the actual owned target, including restored rows;
omitted, readonly and inactive selections retain their exact stored order metadata. A later invalid
relation prevents every earlier reorder. The workbench maps nested gifts and featured pivots this way.
